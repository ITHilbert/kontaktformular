## Sicherheit
- **Mandantentrennung:** nicht betroffen, das Paket hat keine Mandanten.
- **Autorisierung:** Das Feature bringt keine neuen Routen. Die Middleware liest nur Query, Pfad und `Referer` und schreibt in die eigene Session.
- **Validierung/Eingaben:** Nur Strings werden übernommen, getrimmt und auf 255 Zeichen gekürzt. Arrays und unbekannte Schlüssel werden verworfen (`Herkunft::fromArray`, auch beim Lesen aus der Session). Der Referrer-Host wird per `FILTER_VALIDATE_DOMAIN` geprüft. Werte im POST-Body werden nicht gelesen (`$request->query`).
- **Mass-Assignment:** `herkunft` steht neu in `$fillable`. In `src/` gibt es aber kein `fill()`/`create()` mit Request-Daten, der Controller setzt die Spalte nur aus der Session. Ein Besucher kann `herkunft` also nicht über Formularfelder setzen. Es gibt kein Risiko, aber auch keinen Grund für den Eintrag.
- **Ausgabe-Escaping:** In beiden Mail-Views werden die Werte mit `{{ }}` ausgegeben. Der Einstiegspfad kommt vom Besucher und wird im HTML-Teil escaped.
- **Datenschutz (AK6):** Der Klick-ID-Wert erreicht die Mail über `Site:`, siehe Tabelle. Ohne die Mail liegt der Wert serverseitig in Session und Spalte, wie die Spec es vorsieht.
- Hinweis außerhalb des Pakets: Laravel legt die volle URL samt `gclid` ohnehin in `_previous.url` der Session ab. Beim Treiber `cookie` liegt sie damit im Browser-Cookie (im echten Lauf gesehen). Randfall 9 ist damit erfüllt, für die Datenschutzerklärung ist das aber relevant. Außerdem gibt die Host-Debugbar (nur bei `APP_DEBUG`) die Werte im HTML aus. Beides kommt nicht aus dem Paket.

## Fazit: nicht freigegeben
1. **AK6** „Der Wert der Klick-ID steht nie in der Mail“ ist verletzt, sobald das Formular auf einer URL mit `gclid`/`gbraid`/`wbraid` abgeschickt wird, weil `Site:` `window.location.href` ausgibt. Das widerspricht AK8 (`Site:` unverändert). Das muss in der Spec entschieden werden, z. B. Klick-ID-Parameter aus dem Wert von `Site:` entfernen und AK8 auf Bezeichnung und Format beschränken, oder AK6 auf die neuen Zeilen einschränken. Der bestehende Test prüft den Fall nicht.
2. **AK1** gilt nicht für jeden Request über `web`: Bricht eine vorher einsortierte Middleware ab (`Authenticate` per Priorität, CSRF 419, throttle 429), wird nichts erfasst, und der nächste Request wird zum First Touch. Für öffentliche Landingpages hat das kaum Folgen, es widerspricht aber dem Wortlaut. Lösung im Code (Middleware direkt nach `StartSession` einsortieren) oder AK einschränken.
